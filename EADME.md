1\. Queue<T> vs Stack<T>



Queue<T> — очередь, работает по принципу FIFO (First In, First Out): элементы добавляются в конец (Enqueue) и извлекаются из начала (Dequeue). Аналогия — очередь в магазине.



Stack<T> — стек, работает по принципу LIFO (Last In, First Out): добавление и извлечение с одного конца (Push/Pop). Аналогия — стопка тарелок.



Когда применять:



&#x20;   Queue<T> — обработка задач в порядке поступления (очередь сообщений, обход графа в ширину/BFS, буфер событий).



&#x20;   Stack<T> — откат действий (Undo/Redo), обход в глубину/DFS, вычисление выражений, рекурсивные алгоритмы.



Обе структуры имеют Peek() (посмотреть без извлечения), Count, Contains().



2\. Зачем сохранять узел из AddLast



LinkedList<T>.AddLast(T value) возвращает LinkedListNode<T>. Это важно, потому что:



&#x20;   O(1) доступ к узлу для последующих операций: AddAfter, AddBefore, Remove(node) — все они принимают узел и работают за O(1).



&#x20;   Find(value) — O(n), линейный поиск по всей коллекции. Если значение повторяется, Find вернёт первый попавшийся, а не тот, что вам нужен.



&#x20;   В LinkedList нет индексатора, поэтому без сохранённого узла вы теряете главное преимущество связного списка — быстрые вставки/удаления в произвольной позиции.



csharp



var node = list.AddLast(42);   // O(1)

// ... позже

list.AddAfter(node, 43);       // O(1), а не поиск через Find



3\. Индексатор словаря и отсутствующий ключ



Dictionary<TKey,TValue> (и IDictionary) через индексатор dict\[key] при отсутствии ключа бросает KeyNotFoundException. Это сделано, чтобы нельзя было молча получить default(TValue) и перепутать «нет значения» с «значение по умолчанию».



Как избежать:



&#x20;   TryGetValue(key, out var value) — рекомендуемый способ.



&#x20;   ContainsKey(key) перед обращением (двойной поиск — менее эффективно).



&#x20;   GetValueOrDefault(key) (в .NET Core 2.0+) — вернёт default, без исключения.



&#x20;   CollectionsMarshal.GetValueRefOrAddDefault — для продвинутых случаев.



csharp



if (dict.TryGetValue(key, out var v)) { /\* используем v \*/ }





4\. IComparable<T> vs IComparer<T>



&#x20;   IComparable<T> реализуется самим типом — задаёт «естественный» порядок сравнения объекта с другим объектом того же типа. Метод CompareTo(T other).



&#x20;   IComparer<T> — внешний объект-компаратор, реализует Compare(T x, T y). Позволяет задавать разные порядки сортировки для одного типа (по имени, по возрасту и т.д.).



Что произойдёт при Sort() без обоих интерфейсов: List<T>.Sort() использует Comparer<T>.Default, который при отсутствии IComparable<T> (или IComparable) бросит InvalidOperationException с сообщением вида "Failed to compare two elements in the array" (внутри — ArgumentException: At least one object must implement IComparable). Для Array.Sort аналогично. Исключение возникает в момент первого сравнения.



5\. Отложенное (ленивое) выполнение LINQ



LINQ-запрос (для IEnumerable<T>) — это описание, а не результат. Методы вроде Where, Select, OrderBy возвращают новый IEnumerable, но обход исходной коллекции не происходит до момента перечисления.



Обход реально происходит, когда:



&#x20;   вызывается foreach;



&#x20;   вызывается терминальный оператор: ToList(), ToArray(), Count(), First(), Sum(), Any(), Max() и т.п.;



&#x20;   вызывается GetEnumerator() и MoveNext().



Следствия:



&#x20;   Запрос выполнится заново при каждом перечислении.



&#x20;   Если исходная коллекция изменилась между созданием запроса и перечислением — увидите актуальные данные.



&#x20;   «Захват» переменных в лямбдах использует их значения на момент перечисления, а не создания запроса.



&#x20;   OrderBy, GroupBy, Reverse при перечислении буферизуют данные.





6\. IGrouping<TKey, TElement>



IGrouping<TKey,TElement> — это результат группировки GroupBy. Отличается от обычной коллекции:



&#x20;   Наследует IEnumerable<TElement> — то есть это последовательность элементов группы.



&#x20;   Дополнительно имеет свойство Key — значение ключа, по которому сгруппированы элементы.



&#x20;   Одна группа = один уникальный ключ; элементы внутри группы идут в исходном порядке.



Применимые операции: всё, что работает с IEnumerable<TElement> — foreach, Count(), Sum(), Select(), Where(), ToList() и т.д. Плюс чтение Key.

csharp



foreach (IGrouping<string, Order> g in orders.GroupBy(o => o.Customer))

{

&#x20;   Console.WriteLine($"{g.Key}: {g.Count()} заказов");

&#x20;   foreach (var o in g) { /\* ... \*/ }

}



7\. Join и несколько заказов у клиента



Join (внутреннее соединение) сопоставляет элементы двух последовательностей по ключу и возвращает пары «элемент1 + элемент2» для каждого совпадения.



Если у клиента несколько заказов, Join вернёт несколько строк — по одной на каждый заказ:

csharp



var result = customers.Join(

&#x20;   orders,

&#x20;   c => c.Id,

&#x20;   o => o.CustomerId,

&#x20;   (c, o) => new { c.Name, o.OrderId, o.Amount });



Клиент с тремя заказами даст три записи. Клиенты без заказов в результат не попадут (для них нужен GroupJoin / DefaultIfEmpty / left join). Если нужно «один клиент — список заказов», используйте GroupJoin или GroupBy после Join.



8\. Бесконечный итератор и Take(N)



Бесконечный итератор (например, while(true) yield return ...) сам по себе не зависает, потому что итераторы в C# ленивы: тело метода выполняется по одному шагу на каждый MoveNext(). Код не исполняется «весь сразу» — он приостанавливается на каждом yield return и возобновляется при следующем запросе элемента.



Take(N):



&#x20;   берёт только первые N элементов и прекращает перечисление после N-го — вызывает Dispose() у перечислителя, и итератор больше не продвигается;



&#x20;   в foreach условие выхода срабатывает, и цикл завершается.



Поэтому InfiniteSequence().Take(10).ToList() завершится быстро. Опасность — терминальные операторы без ограничения: ToList(), Count(), Sum(), Any() на бесконечной последовательности зависнут (или упадут по переполнению), потому что требуют полного обхода.



9\. Явная реализация IEnumerator IEnumerable.GetEnumerator()



Класс, реализующий IEnumerable<T>, обычно реализует и неуниверсальный IEnumerable. Явная реализация нужна, чтобы:



&#x20;   Скрыть неунверсальный метод из публичного API — пользователь класса видит только типобезопасный GetEnumerator(), возвращающий IEnumerator<T>.



&#x20;   Избежать конфликта сигнатур — оба интерфейса объявляют GetEnumerator(), но с разными возвращаемыми типами; явная реализация позволяет иметь обе версии.



&#x20;   Обеспечить совместимость со старым кодом и foreach по неунверсальному IEnumerable, при этом не «засоряя» IntelliSense.



csharp



public IEnumerator<T> GetEnumerator() { /\* ... \*/ }

IEnumerator IEnumerable.GetEnumerator() => GetEnumerator();



Без этого код, работающий через IEnumerable, не смог бы перечислить вашу коллекцию.



10\. Кольцевой буфер: индекс самого старого элемента



В кольцевом буфере (circular buffer) хранят два индекса: head (куда писать) и count (или tail). Если известны head, tail и вместимость capacity:



&#x20;   Самый старый элемент — по индексу tail, если буфер не пуст.



&#x20;   Если используются head и count: старейший индекс = (head - count + capacity) % capacity.



Пример (head указывает на следующую позицию для записи, count — число элементов):

csharp



int oldestIndex = (head - count + capacity) % capacity;

// при count == 0 — буфер пуст, обращаться нельзя



Ключевой момент — операция по модулю % capacity для «заворачивания» индекса. Если вместо count хранится tail (индекс старейшего), то старейший = tail напрямую, а head = (tail + count) % capacity.



11\. Готовый проект из девяти этапов vs девять отдельных заданий



Преимущества единого проекта:



&#x20;   Целостность и контекст — этапы связаны: результат одного используется в другом, видно, как структуры данных работают вместе, а не в вакууме.



&#x20;   Реальная архитектура — один проект имитирует настоящую разработку: слои, зависимости, эволюция кода, рефакторинг.



&#x20;   Накопительное знание — предыдущие решения переиспользуются, закрепляются; студент видит последствия своих ранних выборов.



&#x20;   Интеграция — учит связывать компоненты (очередь + словарь + LINQ + итераторы), а не решать изолированные задачи.



&#x20;   Меньше дублирования — общие классы, тесты, инфраструктура пишутся один раз.



&#x20;   Постепенное усложнение — от простого к сложному, с ощущением прогресса и «работающего продукта».



&#x20;   Мотивация — итог — цельная программа, а не девять разрозненных файлов.



&#x20;   Проверяемость — сквозные сценарии тестируют взаимодействие, а не только отдельные методы.
